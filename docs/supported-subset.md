# Supported Source DSL

The accepted source language is `uo-solidity-like-dsl-v1`: a restricted,
Solidity-shaped DSL parsed through `solang_parser` and lowered to the
post-resolution Sol AST consumed by Lean. It is not currently a theorem claim
over full Solidity 0.8 semantics.

Accepted source features in this prototype:

- `bool`, `uint256`, `bytes32`, `address`
- arithmetic, bitwise operators, comparisons, and boolean connectives over the
  supported scalar types
- fixed-size arrays with compile-time public length
- fixed-size structs of supported scalar fields
- `if/else`
- bounded `for` loops of the form `for (uint i = 0; i < N; i++)`
- state cells, fixed arrays, and mappings with explicit public capacities in sidecar metadata
- pure/view internal helpers that consist of a single return expression
- `require(expr);`
- `keccak256(abi.encodePacked(...))` on fixed-size arguments
- public environment reads for `msg.sender`, `tx.origin`, `block.number`,
  `block.timestamp`, and `block.chainid`; these are manifest-bound public
  inputs, not secrets
- explicit public getter/setup entrypoints and explicit confidential entrypoints
- single return values on admitted functions
- state-map lowering through sidecar metadata rather than unconstrained native
  Solidity mapping semantics

Rejected:

- inline assembly / Yul
- events, custom errors, `revert`, `try/catch`
- `while`, `do while`, `break`, `continue`
- dynamic arrays, `string`, dynamic `bytes`
- unbounded `mapping`
- inheritance, modifiers, constructors/fallbacks/receive
- early confidential returns
- external calls and unsupported function-call shapes
- multi-expression internal functions beyond single-expression pure/view helpers
- multiple return values
- integer widths other than `uint256`
- in confidential entrypoints, indexing a local or parameter array with
  anything but a compile-time constant below its length. An out-of-bounds read
  of such an array fails the whole call, so a secret index would reveal
  whether it is in bounds. Loops unroll to constant indices, so loops over
  arrays are accepted; selecting an element by a secret index needs an explicit
  loop. State arrays are not affected: an out-of-bounds state-array read
  yields the zero value

The accepted and rejected lists above are exercised by an executable admission
matrix: `results/admission_matrix.json` compiles and runs a case for every
accepted feature and compiles a case for every rejected feature, recording the
diagnostic that names each unsupported feature. It is generated by
`mplus-probe --only admission-matrix`, regenerated by `scripts/run_validation.sh`,
and fails closed through the proof-grade acceptance aggregate (`uo-solc` and
`mplus-probe` remain outside the proof-grade TCB; this is empirical admission
coverage, not a semantic proof).

Sidecar metadata requirements:

- every state object must declare `kind`, `backend`, and confidentiality
- every externally callable entrypoint must have an explicit sidecar stanza;
  public entrypoints must say `confidential: false`, and confidential
  entrypoints must say `confidential: true`
- every entrypoint must declare `returns` as `forbidden`, `public`,
  `declassified`, or `encrypted_to_client`; encrypted client returns are
  supported only on confidential entrypoints and require callers to use the
  runtime return-channel session API
- every entrypoint must declare `status` as `public` or `declassified`
- `returns: declassified` requires `declassifies: [return]`, and
  `status: declassified` requires `declassifies: [success]`
- an entrypoint whose success/abort status depends on secrets must declare
  `status: declassified`. Besides `require`/`abortIf` on secret-dependent
  conditions, this includes every write to a confidential map: a full bounded
  map aborts a write of a new key, and whether a key is new depends on the
  map's confidential contents, even when the key itself is public. The Lean
  admission checker (`checkKernelAdmission`) re-decides this rule, and the
  matching rule for returns, on every emitted kernel program with the flow
  analysis proved sound in `UOToolchain/KernelFlow.lean`
- `returns: encrypted_to_client` must not declare `declassifies: [return]`;
  the host-visible outcome contains ciphertext, nonce, AAD hash, and session
  binding evidence, not the plaintext return
- an entrypoint may set `initializer: true` to mark the one-time public setup
  phase; when a contract has an initializer, other entrypoints default to
  `requires_initialized: true` unless explicitly set otherwise
- writing data or predicates derived from confidential state or secret
  arguments into public state is not supported; confidential releases must use
  the `returns`/`status` declassification or the `encrypted_to_client` channel.
  The `public_state_declassifies` sidecar field is rejected (it conflicted with
  the confidential-object targeting restriction)
- every map must declare a public `capacity`. As in Solidity, a map does not
  tell a zero value from an absent key: writing the zero value deletes the key
  and never overflows, so the capacity bounds the keys with nonzero values,
  and a nonzero write of a new key to a full map aborts the call. The runtime
  routes and the Lean semantics (`Value.mapInsertBounded` in
  `UOToolchain/IRSemantics.lean`) agree on this rule
- map and array capacities must be positive
- confidential entrypoints must declare `secret_args`
- `oram_scheme` must be set explicitly when a proof-grade ORAM path is
  intended; `path_oram_local_posmap_v1` remains capped at capacity `128`.
  Larger maps use `path_oram_private_posmap_v1`, which executes but is not yet
  covered by a theorem (see [`path-oram.md`](./path-oram.md)). Both Path ORAM
  schemes admit multi-access entrypoints (the same map touched more than once
  per call); the surrogate scheme is single-access, and a multi-access
  surrogate entrypoint is rejected at compile time with a diagnostic naming
  the limitation
- gas is not declared in the sidecar: a `public_gas_budget` entry is rejected.
  The compiler derives each entrypoint's public gas into the emitted manifest,
  and the recorded `public_gas_budget` and the runtime `gas_used` are a MODELED
  resource cost under cost model `uo-modeled-resource-cost-v1`
  (confidential entrypoints carry the static cost of their fixed schedule,
  `2000 + statements*11 + expressions*7 + commit_ops*29`; public entrypoints use
  the dynamic execution-metric cost
  `logical_reads*3 + logical_writes*5 + physical_writes*17`). This is not stock
  EVM gas: there is no EVM gas schedule or bytecode backend. `results/overheads.json`
  records this cost model and cross-checks formula exactness for every benchmark
- generated artifacts carry an admitted-package hash over the source-language
  tag, the executable-semantics profile tag, source bytes, canonical sidecar
  metadata JSON, compilation mode, compiler version, toolchain manifest digest,
  and package schema tag; the proof-grade translation bundle requires the source
  and artifact package identities to match

Execution-model notes:

- accepted `uint256` syntax is executed in the EVM unsigned 256-bit domain;
  Rust runtime values, canonical fixed-size encodings, compiler literals, and
  the Lean IR evaluator all normalize arithmetic modulo `2^256`, with division
  or modulo by zero returning zero. This deliberately differs from Solidity
  0.8 checked arithmetic and division/modulo-by-zero revert behavior until a
  versioned Solidity semantics bridge is proved.
- every generated artifact declares an executable-semantics profile tag
  (`uo-evm-modular256-v1`) bound into the admitted-package hash. The tag pins
  the executable divergences from Solidity 0.8 named in these notes: wrapping
  modulo-`2^256` arithmetic, division/modulo-by-zero returning zero, canonical
  fixed-size ABI byte encoding, `require`/abort with rollback, no Solidity
  context variables beyond the admitted public-environment fields, and the
  mock-hash preservation route paired with the real-Keccak runtime primitive.
  The proof-grade checker rejects an artifact whose profile tag is unknown or
  divergent (Rust `AdmittedPackageIdentity::validate_current_toolchain`, Lean
  `ImportedAdmittedPackageIdentity.checkWellFormed`); the structured profile
  model is `uoSolidityLikeDslV1Profile` in `SolidityDialectBoundary.lean`.
- `keccak256(abi.encodePacked(...))` is supported by the runtime with real
  Keccak over canonical fixed-size bytes, but the current Lean source/IR/kernel
  preservation proofs use a deterministic mock hash. They prove preservation
  through the shared abstraction, not value-level equality with the real
  Keccak output.
- The Lean bridge target for regaining a Solidity 0.8 theorem claim is
  `VersionedSoliditySemanticsBridge` in
  `proof/lean/UOToolchain/SolidityDialectBoundary.lean`. It names the required
  obligations for checked arithmetic, division/modulo-by-zero, ABI encoding,
  revert/rollback, and any Solidity context variables beyond the admitted
  public environment fields listed above.
- source-to-kernel correctness is stated for the post-resolution Sol AST / UO
  IR consumed by the Lean model. Parser-level preprocessing remains trusted
  until a raw-source-to-post-resolution witness relation is mechanized.
- confidential entrypoints may target only state objects marked
  `confidential: true`, and those objects may not use raw backends. The direct
  Lean proof-grade checker, compiler lowering, and runtime admission enforce
  the raw-backend restriction; compiler lowering and the proof-grade
  translation checker also enforce the confidential-object restriction.
